실무 IT 산업의 큰 그림

Week 1~4에서 Python 기초를 익혔으니, 이제 그 코드가 실제 IT 서비스에서 어디에 놓이는지 큰 그림을 둘러봅시다. 그림 한 장에 모든 것이 들어 있어요. "이걸 다 알아야 하나?" 부담 없이, "이런 세계가 있구나" 정도만 보시면 됩니다.

SECTION 01

왜 큰 그림을 봐야 할까요?

여러분이 매일 쓰는 인스타, 카톡, 배달의민족, 유튜브 — 이 서비스들은 Python 한 가지 언어로만 만들어지지 않습니다.

수십 개의 언어, 수백 개의 도구가 함께 움직여서 "주문하기" 버튼 한 번이 작동해요. 이걸 한 사람이 다 다루지는 않습니다. 백엔드·프론트엔드·DevOps·데이터 엔지니어가 각자 한두 영역에 집중하고 협력합니다.

그래서 왜 큰 그림을 봐야 하느냐

"백엔드", "DB", "API", "캐시" 같은 단어를 들었을 때 어디 자리에 있는 도구인지 안다는 것이 큰 차이를 만듭니다.

AI가 "Redis 써서 캐시 처리하시면 됩니다"라고 답했을 때, "왜 캐시가 필요한지" 알면 그 답을 검증할 수 있어요.

SECTION 02

한 장으로 보는 IT 산업

초보자가 큰 그림을 잡기 위해 인터넷 서비스를 우선 3개 영역으로 단순화해 보겠습니다. 실제 서비스는 네트워크·보안·운영·데이터 파이프라인 등 더 많은 영역이 함께 움직입니다.

  • Frontend — 사용자가 직접 보고 조작하는 부분
  • Backend — 요청을 받아 규칙에 따라 처리하는 서버 쪽 프로그램
  • Database / 뒷단 서비스 — 데이터를 저장하거나 백엔드의 일을 돕는 시스템
먼저 이것만 기억하세요 — 요청과 응답

사용자가 버튼을 누르면 Frontend가 Backend에 요청(Request)을 보냅니다. Backend는 필요한 데이터를 읽거나 처리한 뒤 응답(Response)을 돌려줍니다. 이때 Backend가 DB·캐시·메시징·외부 API 같은 다른 시스템과 협력할 수 있습니다. 

사용자
  ↓ 클릭
Frontend
  │  HTTP 요청
  ▼
Backend ─────→ Database / Cache / 외부 API
  │                    │
  ◀────────────────────┘
  │  응답(JSON 등)
  ▼
Frontend
  ↓
화면에 결과 표시

실제 시스템은 훨씬 복잡할 수 있지만, 처음에는 "요청이 어디로 가고, 누가 처리하고, 결과가 어디로 돌아오는가"를 따라가면 됩니다.

아래 한 장에 모든 것이 들어 있어요.

그림 5.1 — IT 산업 한 장. Frontend(왼쪽) ↔ Backend(가운데) ↔ Database/뒷단(오른쪽)

SECTION 03

Backend — Python이 사는 곳

버튼 한 번의 Request / Response 흐름

사용자 → Frontend → HTTP Request → Backend
                                ├→ 인증/검증
                                ├→ DB/Cache
                                ├→ 외부 API
                                └→ 비즈니스 로직
사용자 ← Frontend ← HTTP Response ← Backend

Request는 "이 일을 해 달라"는 메시지, Response는 "처리 결과" 메시지입니다. GET/POST/PUT·PATCH/DELETE는 흔히 조회/생성·작업/변경/삭제 의도를 표현합니다.

한 요청 내부에서는 Week 1~4가 그대로 실행됩니다

POST /orders → 인증 → 입력 검증 → if/함수/리스트·dict 처리 → DB 저장 → JSON 응답

인스타에서 좋아요 버튼을 누르면, 그 정보가 인스타 회사의 서버 컴퓨터까지 갑니다.

그 서버에서 데이터베이스에 저장되고, 작성자에게 알림이 보내지고, 피드 정렬이 다시 계산됩니다. 이 모든 처리가 Backend의 일이에요.

"서버"라는 단어 두 가지 의미

  • 서버 컴퓨터 — 다른 프로그램이나 사용자에게 서비스를 제공하도록 운영되는 컴퓨터(물리 서버일 수도 있고 클라우드의 가상 서버일 수도 있음).
  • 서버 소프트웨어 — 그 컴퓨터에서 도는 백엔드 프로그램.

보통 둘 다를 묶어서 "서버"라 부릅니다.

Backend의 5가지 일

  1. 요청 받기 (Frontend의 API 요청을 받음)
  2. 인증 확인 (진짜 본인인가? 토큰 검증)
  3. 비즈니스 로직 처리 (할인 쿠폰 적용 같은 규칙)
  4. DB 입출력 (데이터 저장·조회)
  5. 응답 반환 (결과를 JSON으로 돌려줌)

Backend 언어들

Backend는 다양한 언어로 만들 수 있어요.

  • Python — 이번 과정에서 배운 언어. Django/Flask/FastAPI. 데이터·AI 연계 강점. Instagram·Netflix 등에서 사용합니다.
  • Java — 한국 기업 표준. Spring Boot. 네이버·카카오·토스·배민 모두 사용.
  • JavaScript/TypeScript — Node.js. Frontend와 같은 언어로 백엔드.
  • Go — 구글이 만듦. 동시 처리 강함.
  • Ruby — Ruby on Rails. GitHub·Airbnb·Shopify가 시작.
  • PHP — 오랫동안 웹 백엔드에 널리 사용되어 온 언어. 현재도 많은 서비스와 CMS에서 사용.
  • C# — 마이크로소프트의 .NET.
  • Rust — 메모리 안전성과 성능을 중시하는 시스템 언어로, 일부 백엔드 영역에서도 사용.

Python으로 시작하는 백엔드

Python을 계속 백엔드 방향으로 공부한다면 다음과 같은 웹 프레임워크를 만나게 됩니다.

  • Flask — 가장 작고 학습용으로 좋음.
  • FastAPI — 타입 힌트와 비동기 지원을 잘 활용하는 현대적인 API 프레임워크.
  • Django — 큰 사이트용. Instagram도 사용.

큰 백엔드는 여러 구조를 선택합니다 — 마이크로서비스도 그중 하나

규모가 큰 서비스는 하나의 큰 애플리케이션(모놀리스)으로 운영하기도 하고, 기능을 작은 서비스들로 나누어 운영하기도 합니다. 후자의 대표적인 방식이 마이크로서비스입니다.

예: 회원 서비스 / 가게 서비스 / 주문 서비스 / 결제 서비스 / 배달 서비스 / 알림 서비스. 잘 분리하면 한 부분의 장애가 전체로 번지는 범위를 줄일 수 있습니다. 하지만 서비스끼리 의존하므로 설계가 나쁘면 장애가 전파될 수도 있습니다.

모놀리스가 나쁘고 마이크로서비스가 좋은 건 아닙니다

작은 서비스는 하나의 애플리케이션으로 시작하는 편이 개발·배포가 더 단순할 수 있습니다. 서비스와 조직이 커지면서 독립 배포나 확장이 필요해질 때 마이크로서비스를 선택하기도 합니다. 아키텍처는 유행이 아니라 문제에 맞춰 고르는 선택입니다.

배달의민족은 마이크로서비스 + Java/Spring 조합으로 운영됩니다 (출처: 우아한형제들 기술블로그 2016).

SECTION 04

Database / 뒷단 서비스 — 백엔드 뒤의 세계

메모리의 변수와 Database의 가장 큰 차이 — persistence

실행 중 Python 객체는 프로세스가 끝나면 사라질 수 있지만 Database는 프로그램 재시작 이후에도 필요한 데이터를 지속적으로 보관하기 위한 시스템입니다.

NoSQL을 "스키마가 없는 DB"라고 외우지 마세요

NoSQL은 하나의 데이터 모델이 아니라 Key-Value, Document, Wide-column, Graph 등 서로 다른 모델을 아우르는 범주입니다. Document DB가 문서별 필드를 유연하게 허용할 수 있다고 해서 schema가 전혀 없다는 뜻은 아닙니다.

RDB: users(id, name, age)
→ table/column 구조를 DB가 강하게 관리

Document 예:
{"name":"Kim", "age":30}
{"name":"Lee", "age":25, "interests":["python"]}
→ 구조를 더 유연하게 허용할 수 있음

Document DB도 schema validation을 둘 수 있고 애플리케이션이 기대하는 논리적 schema는 여전히 존재합니다. 핵심은 스키마를 어디에서 얼마나 엄격히 강제하는지가 모델/제품에 따라 다르다는 점입니다.

Key-Value

key로 값 조회

Document

문서 단위 데이터

Wide-column

분산·대규모 접근 패턴

Graph

노드와 관계 탐색

RDB와 NoSQL 중 하나가 무조건 우월한 것이 아니라 데이터 모델, 일관성 요구, 조회/쓰기 패턴, 운영 특성으로 선택합니다.

Cache HIT / MISS와 stale 데이터

요청 → Cache 조회
        ├─ HIT  → 바로 사용
        └─ MISS → DB 조회 → Cache 저장 → 사용

캐시는 보통 원본 그 자체가 아니라 빠른 재사용을 위한 데이터입니다. DB는 바뀌었는데 캐시에 옛 값이 남는 stale 문제 때문에 TTL, 삭제/갱신 같은 invalidation 전략이 필요합니다.

동기 호출과 메시징

동기: Order → Payment → 결과 기다림 → 다음 처리
메시징: Order → OrderCreated 발행 → 자신의 흐름 진행
                           ↓ Broker ↓
                         알림/분석/기타

비동기 구조는 사용자가 모든 후속 완료를 기다리지 않게 할 수 있지만 전체 작업 시간이 무조건 짧아진다는 뜻은 아닙니다.

Image / Container / Kubernetes를 원리로 보기

Docker Image → 실행 → Container A / B / C

Kubernetes
원하는 상태 3개
실제 상태   2개
    ↓ 차이 감지
1개 추가 → 상태를 맞춤

Kubernetes의 핵심 아이디어 하나는 원하는 상태(desired state)와 실제 상태(actual state)를 계속 맞추는 reconciliation입니다. 컨테이너는 일반 VM과 동일한 개념이 아니며 보통 호스트 커널을 공유하며 프로세스를 격리합니다.

백엔드는 혼자 일하지 않습니다. 뒤에는 데이터 보관·캐시·메시지 전달·결제·AI 등이 줄지어 있어요.

그림에 안 보이는 중요한 영역도 있습니다

실무에는 네트워크, 보안, 로그·모니터링, 배포 자동화, 백업 같은 운영 영역도 매우 중요합니다. Week 5에서는 처음 보는 분이 전체 흐름을 놓치지 않도록 우선 애플리케이션과 데이터 흐름에 집중합니다.

Database

회원 정보, 게시글, 주문 내역처럼 오래 보관해야 하는 데이터는 보통 DB에 저장합니다. 모든 데이터를 무조건 DB에 넣는 것은 아니며, 목적에 따라 파일·객체 스토리지·캐시 등 다른 저장소도 함께 사용합니다.

입문 단계에서는 먼저 관계형 DB와 NoSQL 계열이라는 큰 구분으로 살펴보겠습니다. 실제 데이터베이스 분류는 더 다양합니다.

관계형 DB (RDB)

데이터를 표(테이블)로 저장합니다. 표끼리 서로 연결지을 수 있어서 "관계형"입니다.

배달앱이라면 users 표 / stores 표 / orders 표 같은 식. orders가 user_id로 users를 가리키는 구조예요.

은행·쇼핑몰·예약 시스템처럼 데이터가 정확하게 맞아야 하는 곳에 강합니다.

  • MySQL — 가장 흔함. 배달의민족도 AWS Aurora MySQL 사용 (출처: 우아한형제들 기술블로그 2019).
  • PostgreSQL — 기능 풍부. 새 프로젝트가 많이 선택.
  • Oracle — 유료. 대형 은행·금융권.

NoSQL

제품과 데이터 모델에 따라 스키마를 더 유연하게 다룰 수 있다는 점이 강점이 될 수 있습니다. "스키마가 아예 없다"는 뜻은 아닙니다.

  • MongoDB — 문서(document) 형태로 데이터를 저장. 구조가 자주 달라지는 데이터를 다룰 때 선택할 수 있음.
  • Cassandra — 여러 서버에 분산해 대규모 데이터를 처리하도록 설계된 데이터베이스.
  • DynamoDB — AWS의 관리형 DB.
SQL — 백엔드의 다음 학습

관계형 DB에 접근하려면 SQL이라는 언어를 씁니다. 예: SELECT * FROM users WHERE age >= 30; (30살 이상 다 찾기).

MySQL·PostgreSQL·Oracle 같은 대표적인 관계형 DB는 SQL을 사용합니다. 백엔드 개발자가 다음으로 배워야 할 가장 중요한 한 가지가 SQL입니다.

캐시

캐시(Cache)는 자주 쓰는 데이터를 미리 빠른 곳에 저장해두는 방법입니다.

인스타 피드를 매번 DB에서 처음부터 계산하면 너무 느려요. 한 번 계산한 결과를 더 빠르게 접근할 수 있는 저장소에 잠깐 보관하면 같은 요청을 다시 처리할 때 DB 조회나 계산을 줄일 수 있습니다.

대표적으로 Redis를 많이 사용합니다.

Redis로 자주 하는 일

Redis는 메모리 기반 데이터 저장소로, 빠른 접근이 필요한 여러 상황에 활용됩니다. 모든 서비스가 반드시 Redis를 사용하는 것은 아닙니다.

  • 자주 쓰는 데이터 빨리 꺼내기 (캐시 — 가장 흔한 용도)
  • 로그인 세션 보관
  • 실시간 순위 (게임 점수판, 인기 상품)
  • Pub/Sub, Streams 등을 이용한 메시지 전달
  • 여러 서버 간 동시 접근 제어 (분산 락)

메시지 큐

먼저 두 방식을 비교해 봅시다. 동기 호출은 상대 시스템의 답을 기다리는 방식이고, 비동기 메시징은 일을 맡겼다는 메시지를 남겨두고 각 시스템이 나중에 처리할 수 있게 하는 방식입니다. 모든 작업을 메시지 큐로 바꾸는 것은 아니며, 즉시 결과가 필요한 요청은 동기 호출이 더 자연스럽습니다.

메시징 시스템은 한 프로그램이 다른 프로그램의 처리가 끝날 때까지 꼭 붙잡고 기다리지 않도록 메시지를 중간에서 받아 전달하는 우편함/중계소 역할을 합니다.

왜 필요한가?

배민에 주문이 들어오면 백엔드가 매장·라이더·푸시·분석 4곳에 알려야 해요.

직접 차례로 호출하면 한 곳이라도 멈추면 다 멈추고 응답이 늦어집니다.

메시징 시스템에 "주문이 생성됐다"는 이벤트를 발행하면 필요한 시스템들이 각자의 방식으로 받아 처리하도록 설계할 수 있습니다. 한 소비자가 느리거나 일시적으로 멈춰도 전체 요청 흐름을 직접 호출 방식보다 느슨하게 연결할 수 있습니다.

대표적인 도구 중 하나가 Apache Kafka입니다. Kafka는 단순한 작업 큐라기보다 많은 이벤트를 지속적으로 기록하고 여러 소비자가 읽을 수 있는 이벤트 스트리밍 플랫폼에 가깝습니다.

LinkedIn·Netflix·Uber·배달의민족이 모두 사용합니다 (출처: 우아한형제들 기술블로그 2025.6).

작업 큐나 메시지 라우팅이 중심인 시스템에서는 RabbitMQ 같은 메시지 브로커도 많이 사용합니다. Kafka와 RabbitMQ는 규모만으로 나누기보다 필요한 처리 방식에 따라 선택합니다.

검색 엔진

관계형 DB도 텍스트 검색 기능을 제공합니다. 하지만 대규모 전문 검색, 관련도 계산, 형태소 분석, 복잡한 검색 경험이 필요하면 검색 전용 시스템을 따로 두기도 합니다.

예: 배민에서 "치킨" 검색 시 가게명·메뉴명·비슷한 단어·오타 보정·인기순 정렬이 동시에 필요해요. 이런 요구가 커질수록 검색 전용 인덱스와 기능을 활용하는 편이 유리할 수 있습니다.

대표적인 검색·분석 엔진으로 Elasticsearch가 있습니다. 실제 서비스에서는 요구사항에 따라 DB의 검색 기능이나 다른 검색 엔진을 선택하기도 합니다.

결제 — PG사

PG사(Payment Gateway, 결제 대행사)는 온라인 결제를 대신 처리하는 전문 회사입니다.

카드 정보는 보안과 결제 산업의 규정 준수가 매우 중요하기 때문에, 많은 서비스가 PG사나 결제 전문 사업자의 안전한 결제 기능을 연동하는 구조를 사용합니다.

흐름: 쇼핑몰 → PG사 → 카드사 → 은행 → PG사 → 쇼핑몰.

한국에는 NHN KCP, KG이니시스, 토스페이먼츠, 나이스페이먼츠 같은 회사가 있어요.

그 외에 간편결제로 카카오페이·네이버페이·페이코도 있습니다.

푸시 알림

앱이 닫혀있어도 화면 위에 뜨는 메시지 (카톡 알림 같은 것).

일반적인 모바일 앱의 원격 푸시는 운영체제 생태계가 제공하는 푸시 전달 서비스를 통해 기기로 전달됩니다.

  • Android — 구글의 FCM (Firebase Cloud Messaging). 무료.
  • iOS — 애플의 APNs (Apple Push Notification service). 무료.

클라우드

회사가 서버를 직접 구입해 운영할 수도 있고, 클라우드 사업자의 컴퓨팅·저장소·DB 같은 자원을 빌려 사용할 수도 있습니다. 오늘날에는 두 방식을 함께 쓰는 경우도 많습니다.

클라우드는 필요한 IT 자원을 API나 콘솔로 빠르게 만들고 줄일 수 있다는 장점이 있습니다. 서비스에 따라 사용량 기반, 예약형, 정액형 등 여러 과금 방식이 있습니다.

세계적으로 AWS, Microsoft Azure, Google Cloud가 대표적인 대형 클라우드 사업자입니다.

  • AWS (Amazon Web Services) — 컴퓨팅·스토리지·DB 등 매우 다양한 클라우드 서비스를 제공.
  • Azure (Microsoft) — Microsoft 생태계 및 기업 환경과 폭넓게 연계.
  • Google Cloud — 데이터·AI를 포함한 다양한 클라우드 서비스를 제공.

국내에도 NAVER Cloud, NHN Cloud 등 여러 클라우드 사업자가 있습니다.

컨테이너

"내 컴에선 잘 돌았는데요"

개발자 노트북에선 코드가 잘 돌았는데 회사 서버에선 안 도는 경우가 많았어요. Python 버전·라이브러리·환경이 달라서요.

Docker를 사용하면 애플리케이션과 필요한 파일·라이브러리·설정을 이미지로 묶고, 이를 격리된 컨테이너로 실행할 수 있습니다. 호환되는 환경 사이의 차이를 크게 줄여 주지만, CPU 구조·운영체제 기능·외부 설정까지 모든 차이를 없애 주는 것은 아닙니다.

Kubernetes(쿠버네티스, k8s)는 많은 컨테이너화된 애플리케이션을 원하는 상태로 운영하도록 돕는 오케스트레이션 시스템입니다. 실패한 워크로드를 다시 실행하거나 교체하는 self-healing 기능이 있고, 설정하면 부하에 따라 수평 확장도 할 수 있습니다.

AI 서비스

최근에는 기존 서비스에 AI 모델이나 AI API를 연결하는 사례도 빠르게 늘고 있습니다.

백엔드가 외부 AI API를 호출하거나 자체 모델을 서비스에 연결해 요약·검색·추천·대화 같은 기능을 추가할 수 있습니다.

  • Anthropic Claude — 대화·문서·코딩 등 다양한 작업에 활용되는 AI 모델/서비스.
  • OpenAI — GPT 계열 모델과 API를 제공하며 다양한 애플리케이션에서 활용.
  • Google Gemini — 텍스트와 이미지 등 여러 형태의 입력을 다루는 모델과 API를 제공.
  • Meta Llama — 공개 가중치 모델 계열로, 라이선스 조건에 따라 자체 환경에서 운영할 수 있음.

여러분이 배운 Python으로 AI API를 호출하는 작은 프로젝트는 파일·JSON·API·함수를 한 번에 복습하기 좋은 실습 주제가 될 수 있습니다.

4주차 브라우저 실습에서는 pyfetch를 사용했지만, 일반적인 로컬 Python 프로그램에서는 requests나 httpx 같은 HTTP 라이브러리를 사용하는 경우가 많습니다.

SECTION 05

시뮬레이터 — 배달앱 주문 흐름 예시

시뮬레이터를 볼 때 화살표의 의미를 읽으세요

App→Backend는 HTTP 요청, Backend→DB는 조회/저장, Backend→PG는 외부 API 호출, Backend→Broker는 이벤트 발행처럼 같은 화살표라도 무엇이 이동하는지가 다릅니다. 동기 호출과 메시지 발행도 구분해서 보세요.

위에서 본 모든 게 어떻게 함께 움직이는지 시뮬레이터로 따라가 봅시다.

배달앱에서 주문 한 번이 여러 시스템을 거칠 수 있는 예를 10단계로 보여드려요.

교육용 예시입니다

일부 기술은 우아한형제들이 과거 공개한 기술 자료를 참고하고, 나머지는 일반적인 IT 아키텍처 패턴을 이용해 연결했습니다. 현재 배달의민족의 실제 주문 내부 구조를 그대로 재현한 그림은 아닙니다. 실무 시스템은 계속 바뀌고 내부 세부 구조도 공개되지 않는 경우가 많습니다.

주문 한 번에 8개 시스템 협력

이 교육용 예에서는 모바일 앱 + 백엔드 + DB + 결제 + 메시징 + 매장 + 라이더 + 푸시처럼 여러 시스템이 협력합니다.

실제 서비스에서는 여기에 네트워크·클라우드·결제 사업자·푸시 전달 서비스·로그/모니터링 등 더 많은 구성 요소가 추가될 수 있습니다.

사진 업로드, 메시지 전송, 동영상 재생 같은 다른 서비스도 세부 구조는 다르지만 여러 시스템이 요청·저장·처리를 나눠 맡는다는 공통점을 가집니다.

"내가 다 알아야 하나?" — 아닙니다

한 사람이 다 다루지 않습니다. 백엔드·프론트엔드·DevOps·데이터·모바일 개발자가 각자 한두 영역에 집중하고 협력해요.

여러분이 Python으로 시작했다면 Backend 또는 뒷단 일부에 자연스럽게 닿게 됩니다.

5주차 핵심 정리
  • 인터넷 서비스의 큰 그림: Frontend ↔ Backend ↔ Database/뒷단.
  • Frontend: HTML/CSS/JS, React, Vue, Swift, Kotlin, Flutter.
  • Backend: Python, Java, JavaScript/TypeScript, Go, Ruby, PHP, C#, Rust 등. 구조는 모놀리스·마이크로서비스 등 요구사항에 따라 선택.
  • Database: MySQL, PostgreSQL, MongoDB, Oracle.
  • 뒷단: 캐시(Redis), 메시지 큐(Kafka), 검색(Elasticsearch), 결제(KCP/토스페이먼츠), 푸시(FCM/APNs), 클라우드(AWS), AI(Claude/ChatGPT/Gemini).
  • 주문 1번에 8개 이상 시스템 협력.
  • 한 사람이 다 다루지 않음. 시작점이 중요.

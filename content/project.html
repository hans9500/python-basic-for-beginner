종합 프로젝트 · Pygame

공 피하기 게임 — 배운 Python을 실제 프로그램으로 연결하기

이 탭의 목적은 Pygame API를 많이 외우는 것이 아닙니다. 지금까지 배운 변수, 조건문, 반복문, 리스트, 딕셔너리, 함수가 실제 게임 안에서 왜 필요한지 하나의 프로그램을 만들며 확인합니다.

브라우저에서 실행하는 Pygame

이 강의의 일반 예제는 Pyodide에서 실행됩니다. 이 프로젝트는 같은 Pyodide에 pygame-ce를 추가로 불러와 Canvas에 게임 화면을 그립니다.

브라우저는 화면 갱신 기회를 받아야 하므로 데스크톱 Pygame의 전형적인 무한 루프와 달리, 이 예제의 게임 루프는 async/await로 브라우저에 제어권을 잠깐씩 돌려줍니다.

SECTION 01

먼저 게임을 프로그램의 상태 변화로 보기

공 피하기 게임을 그림으로 보기 전에 Python 관점으로 다시 보겠습니다. 게임은 매 순간 현재 상태를 읽고 → 입력에 따라 상태를 바꾸고 → 그 상태를 화면에 그리는 반복입니다.

   ↓

   ↓
공 위치 변경
   ↓
충돌 검사
   ↓
화면 그리기
   ↓
다시 처음으로

여기서 이미 배운 문법이 그대로 등장합니다.

  • while — 게임을 계속 반복
  • if — 키가 눌렸는지, 충돌했는지 판단
  • 변수 — 플레이어 좌표, 속도, 점수 같은 현재 상태 저장
  • 리스트 — 화면에 존재하는 여러 공을 함께 관리
  • 함수 — 이동, 생성, 그리기, 충돌 같은 역할을 분리
핵심
게임이라서 새로운 Python이 생기는 것이 아닙니다. 앞에서 배운 Python 문법이 더 구체적인 목적을 갖게 되는 것입니다.

SECTION 03

게임 루프 — Week 2의 while이 실제 프로그램이 되다

일반적인 Pygame 프로그램의 중심은 게임 루프입니다.

running = True

while running:
    # 1. 입력 확인
    # 2. 상태 변경
    # 3. 충돌 계산
    # 4. 화면 그리기
    pass

while running:은 조건이 참인 동안 본문을 반복한다는 Week 2의 원리 그대로입니다. 단지 이번에는 한 번의 반복을 보통 한 프레임(frame)이라고 부릅니다.

그런데 브라우저에서는 왜 await가 필요한가?

나쁜 형태
Python while이 CPU를 계속 점유
        ↓
브라우저가 Canvas를 화면에 갱신할 기회가 없음

브라우저용 형태
한 프레임 계산
        ↓
pygame.display.flip()
        ↓
await asyncio.sleep(...)
        ↓
브라우저에 잠깐 제어권 반환
        ↓
다음 프레임
async def game_loop():
    while running:
        # 입력, 계산, 그리기
        pygame.display.flip()
        await asyncio.sleep(1 / 60)

이 await는 Pygame의 핵심 문법이 아니라 브라우저에서 실행하기 위해 필요한 실행 환경상의 차이입니다. 데스크톱 Pygame에서는 보통 pygame.time.Clock()으로 프레임 속도를 조절합니다.

SECTION 04

키보드 입력 — if가 플레이어를 움직인다

키보드 상태를 얻은 다음 조건문으로 어떤 키가 눌렸는지 검사합니다.

keys = pygame.key.get_pressed()

if keys[pygame.K_LEFT]:
    player_x -= speed

if keys[pygame.K_RIGHT]:
    player_x += speed

여기서 if는 단지 흐름을 나누고, 실제 상태 변화는 player_x -= speed와 player_x += speed가 담당합니다.

왼쪽 키가 눌림?
├─ False → 아무 변화 없음
└─ True  → player_x -= speed
                ↓
          다음 프레임의 위치가 달라짐

그리고 화면 밖으로 나가지 않게 값을 제한합니다.

player_x = max(0, min(WIDTH - PLAYER_W, player_x))

Self Study에서 본 min(), max()가 실제로 좌표의 범위를 제한하는 데 쓰이는 예입니다.

SECTION 05

공이 여러 개라면 — list와 dict가 필요한 이유

공 하나라면 ball_x, ball_y 두 변수로도 충분합니다. 하지만 공이 5개, 10개가 되면 변수를 계속 추가하는 방식은 곧 무너집니다.

balls = [
    {"x": 100, "y": 20, "speed": 4},
    {"x": 300, "y": 80, "speed": 5},
    {"x": 500, "y": 40, "speed": 3},
]

for ball in balls:
    ball["y"] += ball["speed"]

이 구조에는 Week 3의 핵심이 그대로 들어 있습니다.

  • balls — 여러 공을 순서대로 관리하는 list
  • 각 공 — x, y, speed라는 이름으로 상태를 묶은 dict
  • for ball in balls — 모든 공에 같은 이동 규칙 적용
balls
  │
  ├──▶ {x, y, speed}  공 1
  ├──▶ {x, y, speed}  공 2
  └──▶ {x, y, speed}  공 3

for문은 공을 하나씩 ball이라는 이름에 연결해서 처리

공이 화면 아래로 빠져나가면 새 위치로 되돌립니다. 여기서 random이 실제 게임 규칙에 쓰입니다.

if ball["y"] > HEIGHT:
    ball["x"] = random.randint(0, WIDTH - BALL_SIZE)
    ball["y"] = -BALL_SIZE
SECTION 06

충돌 판정 — 객체 두 개의 영역이 겹치는가?

플레이어와 공을 사각형 영역으로 표현하면 Pygame의 Rect가 서로 겹치는지 검사할 수 있습니다.

player_rect = pygame.Rect(player_x, player_y, PLAYER_W, PLAYER_H)
ball_rect = pygame.Rect(ball["x"], ball["y"], BALL_SIZE, BALL_SIZE)

if player_rect.colliderect(ball_rect):
    running = False
player_rect.colliderect(ball_rect)
              ↓
          True / False
              ↓
         if가 판단
              ↓
True라면 running = False
              ↓
while 조건이 False가 되어 게임 종료

여기서 중요한 것은 Pygame의 메서드 이름을 외우는 것이 아니라, 함수/메서드 호출이 결과 객체를 반환하고 그 결과를 if가 판단한다는 앞선 원리가 그대로 적용된다는 점입니다.

SECTION 07

함수로 나누기 — 코드가 길어서가 아니라 역할이 달라서

게임 코드가 커지면 모든 일을 게임 루프 안에 넣을 수는 있지만 읽기가 어려워집니다. 기능이 아니라 역할을 기준으로 함수를 나누면 흐름이 보입니다.

def move_player(player_x, speed):
    ...
    return player_x


def update_balls(balls):
    ...


def hit_player(player_rect, balls):
    ...
    return True or False

그러면 게임 루프는 세부 구현보다 전체 순서를 보여주는 코드가 됩니다.

while running:
    player_x = move_player(player_x, speed)
    update_balls(balls)

    if hit_player(player_rect, balls):
        running = False

    draw_game(...)
함수의 이유
“코드를 짧게 만들기 위해”만 함수로 나누는 것이 아닙니다. 프로그램의 서로 다른 책임을 이름 붙여 분리하면 전체 실행 흐름을 읽기 쉬워집니다.

SECTION 09

도전 프로젝트 — 벽돌깨기

공 피하기에서 배운 게임 루프, 좌표, 키 입력, 상태 변경, 충돌 판정을 그대로 사용하되 규칙을 한 단계 확장해 봅니다. 이번에는 공이 벽과 패들에 부딪히면 방향이 바뀌고, 벽돌과 충돌하면 해당 벽돌이 사라집니다.

키 입력 → 패들 이동
             ↑
             │ 공이 패들에 충돌
             │
공 이동 → 벽/벽돌 충돌 검사 → 속도 방향 변경
                    ↓
               벽돌 제거
                    ↓
                  점수 증가

여기서 새롭게 눈여겨볼 것은 속도도 상태라는 점입니다. 공이 오른쪽으로 움직일 때 ball_dx가 양수라면, 벽에 부딪힌 뒤 ball_dx = -ball_dx로 바꾸는 것만으로 왼쪽 이동이 됩니다.

공 피하기와 무엇이 달라졌나?

  • 공 피하기: 공은 아래로 이동하고 충돌하면 게임이 끝납니다.
  • 벽돌깨기: 공은 x/y 두 방향으로 움직이며 충돌할 때 속도의 부호를 바꿔 반사합니다.
  • 벽돌: 여러 벽돌을 list로 관리하고 충돌한 벽돌만 pop()으로 제거합니다.
  • 게임 상태: 점수뿐 아니라 목숨과 남은 벽돌 개수도 상태가 됩니다.

두 게임을 다시 읽어보기 — 문법이 아니라 연결을 확인

두 게임을 실행한 뒤 아래 질문에 답해 보세요. 정답을 외우는 것보다 각 코드에서 어떤 상태가 바뀌고 어떤 조건이 다음 흐름을 결정하는지 설명할 수 있는지가 중요합니다.

  1. 공 피하기에서 balls가 list이고 각 원소가 dict인 이유는 무엇인가?
  2. for ball in balls에서 ball은 매 반복마다 무엇을 가리키는가?
  3. ball["y"] += ball["speed"]은 게임 상태를 어떻게 바꾸는가?
  4. collided()가 True를 반환하면 그 반환값은 어디에서 사용되는가?
  5. running = False가 왜 게임을 종료시키는가?
  6. 공 하나만 사용할 때보다 list가 필요한 이유는 무엇인가?
  7. 함수를 없애고 전부 main() 안에 쓸 수도 있는데 왜 나누었는가?
  8. 벽돌깨기에서 ball_dx = -ball_dx는 객체를 화면에서 실제로 돌리는 명령일까, 아니면 다음 프레임의 상태를 바꾸는 것일까?
  9. bricks.pop(hit_index) 후 다음 프레임에서 해당 벽돌이 보이지 않는 이유를 list 상태와 그리기 과정으로 설명할 수 있는가?
